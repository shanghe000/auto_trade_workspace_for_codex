# 架构设计

## 目标

构建一个独立的交易工作空间，让 Codex 不是单纯回答交易问题，而是能够在清晰边界下完成：

- 数据采集
- 多 agent 分析
- 策略选择
- 风险审查
- 执行准备与执行
- 事件跟踪
- 复盘与飞书回传

## 适用范围与非目标

### 适用范围

- `15m-4H` 级别的日内 / 波段辅助交易
- “先生成计划，再执行”的半自动交易
- 强可观测、强审计、强边界的低到中频交易工作流

### 非目标

- 把 AI 放在超短线热路径里
- 追求秒级以下反应速度
- 无风控约束的自动交易
- 未经审核的 AI 策略直接上生产

## 顶层分层

```text
飞书 / cc-connect
  -> 主 agent（control plane）
  -> 确定性采集 / 风控 / 执行 / 事件监听（data plane）
  -> 分析 agent / 复盘 agent（analysis plane）
  -> state/ 中的事件、快照、journal、报告（observability plane）
```

## 角色定义

### 1. 主 agent

主 agent 是这个工作空间的总控台。

它负责：

- 接收用户请求
- 创建 `run_id`
- 固定本轮 `snapshot_id`
- 拉起分析 agent
- 形成单一候选 `TradeIntent`
- 把候选意图交给风控和执行层
- 消费订单事件回流
- 输出飞书总结

它不负责：

- 自己去充当订单事件监听器
- 自己直接实现幂等下单
- 自己随意改风控或激活策略

### 2. 分析 agent

建议按长期稳定职责拆成几类：

- `market_structure_agent`
  - K 线结构
  - 趋势 / 盘整 / 失效
  - 关键区间
- `derivatives_flow_agent`
  - OI
  - 成交量
  - 资金费率
  - 多空和杠杆相关指标
- `strategy_research_agent`
  - 产出新策略草案
  - 只负责研究，不负责激活
- `post_trade_review_agent`
  - 开仓后 / 平仓后复盘
  - 输出经验与软风险反馈

这些 agent 的共同边界是：

- 读取同一份冻结快照
- 返回结构化结论
- 不直接下单
- 不直接变更硬风控

### 3. 确定性服务

真正需要低延迟、可重试、可幂等的部分，应做成确定性服务或工具：

- `market_collector`
- `account_collector`
- `risk_engine`
- `execution_gateway`
- `order_event_watcher`
- `reconciliation_checker`

这是本架构的关键设计判断：

- AI 做分析和解释
- 服务做采集、闸门、执行、监听

## 为什么不适合超短线

这套架构里的分析、汇总、审核、执行并不是零成本。

因此：

- 分析 agent 的结果天然有时间延迟
- 主 agent 汇总也有链路延迟
- 执行前还要做二次校验

这意味着它更适合：

- 明确信号窗口能容纳几十秒到几分钟处理时间的策略
- 允许执行前重新确认条件是否仍成立的策略

不适合：

- 1m 以下依赖即时盘口突发变化的抢跑型策略
- 需要把毫秒级盘口变化直接转成动作的系统

## 标准运行流程

### 阶段 1：冻结输入

1. 主 agent 创建 `run_id`
2. `market_collector` 刷新市场快照
3. `account_collector` 刷新账户、持仓、挂单快照
4. 生成本轮固定的 `snapshot_id`

这里的关键原则是：

- 本轮分析只读同一份快照
- 不允许不同分析 agent 各自再去取自己的行情视图

### 阶段 2：并行分析

主 agent 读取当前已 `armed` 的策略集合，并按本轮市场级别挑选候选策略。

之后并行拉起：

- `market_structure_agent`
- `derivatives_flow_agent`
- 必要时的 `risk_review_agent`

它们输出的应是结构化结果，而不是散文式聊天记录。

### 阶段 3：形成候选 TradeIntent

主 agent 汇总：

- 冻结快照
- 当前账户状态
- 当前已激活策略
- 分析 agent 的结论

然后只形成三类结果之一：

- `HOLD`
- `RiskBlocked`
- `TradeIntent`

这里要避免“给多个互相冲突的主意”。除非明确在做方案比较，否则只产出一个主方向。

### 阶段 4：硬风控审查

`risk_engine` 对候选 `TradeIntent` 做确定性审查。

至少检查：

- 策略是否处于 `armed`
- 当前运行模式是否允许执行
- live 开关是否开启
- kill switch 是否关闭
- 品种是否在白名单
- 仓位、杠杆、总暴露是否超限
- 快照是否新鲜
- 是否存在未解决对账异常

只有全部通过，才允许进入执行准备。

### 阶段 5：执行前二次校验

这是本架构非常关键的一步。

因为分析结果基于“分析开始时的市场”，而真正下单时市场可能已经变化。

因此在执行前，必须再次刷新一份更近的快照，并做确定性检查，例如：

- 价格漂移是否超过阈值
- 点差是否恶化
- 成交量 / OI / 盘口是否剧变
- 信号年龄是否超过允许窗口

如果不满足，就直接作废本轮信号并返回主 agent。

### 阶段 6：执行

`execution_gateway` 负责：

- 下单
- 改单
- 撤单
- 返回标准化执行结果
- 写执行 journal

它不能自己创造交易理由，只能执行已经通过审查的意图。

### 阶段 7：事件回流

`order_event_watcher` 负责持续感知：

- 新订单
- 部分成交
- 全部成交
- 撤单
- 止损 / 止盈触发
- 仓位变化
- 账户权益变化

它应把事件标准化为 `OrderEvent`，写入：

- `state/events/*.jsonl`

并根据事件类型决定是否需要重新唤起主 agent。

### 阶段 8：复盘闭环

当出现关键成交或平仓事件时，主 agent 可继续拉起：

- `post_trade_review_agent`

产出内容包括：

- 执行是否符合原策略
- 风险暴露是否合理
- 哪些判断有效
- 哪些条件应降权

这里的输出只能更新**软风险状态**和复盘建议，不能直接改硬风控阈值。

## 订单事件监听怎么做

在目标态下，`order_event_watcher` 应是一个常驻确定性服务。

建议实现方式：

1. 启动时用 REST 拉一次基础状态。
2. 常驻私有 WebSocket 连接。
3. 订阅：
   - `orders`
   - `balance_and_position`
   - 可选 `positions`
4. 把事件归一化并落到本地事件流。
5. 在断线或重连后用 REST 补偿对账。

这一层不应由 AI 代理来承担。

## 运行模式

### 模式 A：manual_confirm

这是 `Human-in-the-loop`。

适合：

- 你希望系统先做足研究，再由你拍板
- 你还在验证策略是否值得真正自动化

规则：

- 主 agent 可以推进到风控通过
- 执行前必须等人工确认
- 每笔关键动作都有 journal 和摘要

### 模式 B：guarded_auto

这是 `Human-on-the-loop`。

适合：

- 你已经有明确策略与预算
- 你允许系统在边界内低频自动执行

规则：

- 只允许 `armed` 策略运行
- 只允许在配置好的预算和时段里运行
- 异常时必须立刻回到人工接管

## 策略治理

策略的治理要点如下：

- 产出：可以来自你自己、研究 agent、复盘 agent
- 审核：必须包含结构审核、风险审核、人工复核
- 激活：只能人工把策略切到 `armed`
- 使用：主 agent 只读取已激活且匹配当前上下文的策略
- 复盘：复盘 agent 可以提出修改建议，但不能直接生效

详细规则见 `strategy-governance.md`。

## 安全不变量

- 没有真实风险配置文件时，不允许 live 交易
- AI 不能自行激活新策略
- AI 不能绕过 `risk_engine`
- 分析结果过期后不能强行执行
- 执行错误不能静默吞掉
- 没有快照、事件和 journal 的交易视为不可接受
